# MyGo PDF development plan

MyGo PDF is a third-party component for MyGo desktop apps. The initial release uses Go `1.27.4`, MyGo `v0.10.0`, and PDFium `chromium/8179`. See the [design](design.md) for current contracts and package responsibilities.

## Product goals

The same component supports live previews and standalone reading. Editors can refresh a PDF while preserving its image and reading position. Desktop apps can build controls around the viewer. The example demonstrates both toolbar and toolbar-free use.

The initial release supports local PDFs and host-generated bytes on macOS, Windows, and glibc Linux for amd64 and arm64. Later releases add search, outlines, passwords, and on-demand reads. Mobile, the web, remote loading, editing, interactive forms, printing, and OCR are outside the `v1.0` scope.

## Technical direction

The viewer uses continuous pagination, viewport tiles, and atomic document refresh. Its lifecycle design draws on MyGo's upstream PDF proposal. The public API lives in the `pdf` package, with native handles and PDFium types kept internal. The host owns file reads, path validation, document generation, and opening the original file in another app. [MyGo PDF proposal](https://github.com/egoist/mygo/pull/124)

- **pdfrx** provides a controller for page navigation, zoom, fit, and viewport state. Use PDFium's progressive API to yield at native pause points. Serialize calls within the process. Complex pages can still exceed a single time slice. [pdfrx controller](https://github.com/espresso3389/pdfrx/blob/5476a917729fade064e0d8af279554db72644c11/packages/pdfrx/lib/src/widgets/pdf_viewer.dart#L6360) · [PDFium progressive rendering API](https://pdfium.googlesource.com/pdfium/+/refs/heads/chromium/8179/public/fpdf_progressive.h)
- **PDF.js** transforms the current image during zoom. Fill missing visible-page previews first, render high-resolution details next, then prefetch one page in the scroll direction. Keep up to one extra tile around the viewport and evict the farthest tiles first. Preserve the anchor's distance from the page edge when zooming in a gap. [PDF.js zoom](https://github.com/mozilla/pdf.js/blob/3471ae1691e1d08cbe7ae2a751259bbfdda3acf1/web/pdf_viewer.js#L1605) · [PDF.js rendering queue](https://github.com/mozilla/pdf.js/blob/3471ae1691e1d08cbe7ae2a751259bbfdda3acf1/web/pdf_rendering_queue.js#L104)
- **React-PDF** separates page display from host controls. Cache text and link geometry by document generation and page, and reuse it across zoom and bitmap changes. Hosts supply toolbars, progress indicators, and outlines as needed. [React-PDF Page API](https://github.com/wojtekmaj/react-pdf/blob/bb19ba0dd2e5cfe3d3a813f104811d0ff50c9203/packages/react-pdf/README.md#page)

## Verification and releases

- **Automated tests.** Run `mise run ci` for every release. Required integration tests must fail when PDFium is missing. Use generated or redistributable PDFs covering mixed page sizes and crops, Chinese and RTL text, copy restrictions, passwords, malformed files, long documents, and complex scans. Use each of the six targets' matching libraries.
- **Performance.** Use the [recorded performance baseline](performance.md) for comparisons. Use the same hardware, samples, and scripts, and record MyGo and PDFium versions. Run at least 30 cold opens and three scripted gesture runs. Report P50 and P95 for time to first visible bitmap, time to complete the first viewport, gesture frame time, time to sharp output, and peak RSS across the runs. For ordinary documents, later releases must keep P95 first-viewport and gesture frame times within `110%` of the baseline. The `v0.2` zoom benchmark for 10,000 pages should allocate at most `10%` of the baseline per operation. Full-page and tile caches have budgets of 24 MiB and 40 MiB. Track in-flight bitmaps, native heap, and GPU memory separately. A newly displayed document generation must cover the actual viewport.
- **Native verification.** Check keyboard, mouse, clipboard, DPI changes, and shutdown on macOS, Windows, and Linux under Wayland and X11. Check pinch gestures with suitable hardware on macOS, Windows, and Wayland. Check modifier-wheel and keyboard zoom on X11. Record real-window and installer results for each platform. [MyGo platform input code](https://github.com/egoist/mygo/tree/v0.10.0/internal)
- **Packaging.** The plugin manifest declares platform-specific PDFium libraries and a shared license notice file. The plugin release tool verifies the pinned upstream archives and library checksums, extracts the release binaries, and consolidates the original notice text. MyGo verifies and bundles both assets during host builds. At runtime the library loads from the app bundle or an explicit path. [MyGo manifest loader](https://github.com/egoist/mygo/blob/v0.10.0/cmd/mygo/natives.go#L45) · [PDFium archives](https://github.com/bblanchon/pdfium-binaries/releases/tag/chromium/8179)
- **Versions and rollback.** Hosts pin a version and can return to the previous tag if a regression occurs. A SHA-256-verified cache can serve resources during an upstream outage. Official macOS installers require signing credentials.

## Release procedure

1. Set `mygo.json` to the next MyGo PDF version. The plugin manifest can keep using its current PDFium asset release when the binaries and license notices are unchanged. The assets published with `v0.1.1` are the initial shared set.
2. Run `mise run ci`, then commit and push the release commit. Start the [Release workflow](../.github/workflows/release.yml) manually from Actions or with `gh workflow run release.yml --ref main`. It runs native PDFium integration tests on all six targets and checks the assets referenced by the manifest against the pinned inputs.
3. Wait for the workflow to succeed and confirm that it ran on the exact commit you intend to tag. Create and push the matching `v*` tag for that commit. Go users can fetch a public tag as soon as it is pushed.
4. On a tag push, the workflow checks the tag against `mygo.json` and looks for a successful manual run on the tagged commit before creating the GitHub Release. Rerun a failed verification for a transient service or download failure. If the untagged commit needs a correction, verify the new commit before tagging it. If the tagged source needs a correction, release it under a new patch version.

When changing PDFium, update the pinned upstream version and SHA-256 values in `cmd/pdfium-resources`. When either the binaries or their license notices change, use a new asset tag such as `pdfium-8179-r2` for a revision of the `8179` assets:

```sh
go run ./cmd/pdfium-resources -release=pdfium-8179-r2
gh release create pdfium-8179-r2 --latest=false \
  --title "PDFium 8179 assets (revision 2)" --notes "PDFium binaries and license notices for MyGo PDF." \
  build/pdfium-release/darwin-*-libpdfium.dylib \
  build/pdfium-release/linux-*-libpdfium.so \
  build/pdfium-release/windows-*-pdfium.dll \
  build/pdfium-release/pdfium-notices.txt
```

Verify that all seven files are publicly downloadable and match the generated files. Copy `build/pdfium-release/mygo-plugin.json` to `internal/pdfium/mygo-plugin.json` and include it in the next MyGo PDF release commit. Keep previously published asset releases available for hosts pinned to earlier Go module versions.

If upstream MyGo adds continuous viewports and atomic refresh, reassess rendering, API, and packaging compatibility. Contribute shared improvements upstream where possible.
